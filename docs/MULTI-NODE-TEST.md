# 多节点实测：两个实例抢任务与崩溃接管

这份文档记录一次真实运行的多节点实验：两个后端实例连同一个数据库，各自 2 个判题槽位，灌入 10 条提交，然后在有任务正在执行时强杀其中一个实例，观察任务是否被另一个实例接管、是否出现重复判题。

结论先说：**接管成立，没有重复判题，没有脏数据。** 两遍从零重建数据库各跑一次，结论一致。

## 一、实验设置

| 项 | 值 |
| :--- | :--- |
| 实例 | node-a（18900）、node-b（18901），同一台机器、同一个 MySQL 库 |
| 沙箱 | `local` 模式（实验只关心调度，不关心隔离） |
| 槽位 | 每实例 2 个（`judgex.worker.concurrency=2`） |
| 租约 | **10 秒**（生产 45 秒，为在十几秒内观测回收而临时缩短） |
| 心跳 | **1 秒**（生产 3 秒） |
| 看门狗 | 5 秒扫描一次过期任务（生产相同） |
| 提交 | 10 条 Python 提交，程序读入后 `sleep(1.2)` 再输出，保证杀节点时有任务在跑 |
| 强杀时机 | 提交完成后第 8 秒，`SIGKILL` node-a |
| 观察方式 | 每 0.5 秒查一次 `judge_tasks`，记录状态与 worker 归属 |

> 租约与心跳是唯一被改的参数，其余（条件更新认领、看门狗回收、延时消息、发件箱）与生产配置完全相同。**不要把这里的 7～10 秒当成生产表现**：生产租约 45 秒，最坏接管时间在 50 秒量级。

## 二、结果

### 总览

| 指标 | 第 1 遍 | 第 2 遍 |
| :--- | ---: | ---: |
| 提交数 / HTTP 失败 | 10 / 0 | 10 / 0 |
| 最终 DONE | 10 | 10 |
| 最终 QUEUED / ASSIGNED / DEAD | 0 / 0 / 0 | 0 / 0 / 0 |
| 尝试次数 = 1 | 8 条 | 8 条 |
| 尝试次数 = 2 | 2 条（#5、#6） | 2 条（#5、#6） |
| 尝试次数 ≥ 3 | 0 条 | 0 条 |
| 杀节点 → 全部终态 | 23.1 秒 | 23.0 秒 |

### 强杀前的归属快照

| 遍 | node-a 在跑 | node-a 已完成 | node-b 在跑 | node-b 已完成 | 仍在排队 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 1 | 2（#5、#6） | 2 | 0 | 2 | 4 |
| 2 | 2（#5、#6） | 2 | 2（#7、#8） | 2 | 2 |

### 被接管的每一条

| 遍 | 提交 | 杀 → 重新排队 | 杀 → 被 node-b 认领 | 杀 → 判完 | 尝试次数 | 最终节点 |
| :--- | :--- | ---: | ---: | ---: | ---: | :--- |
| 1 | #5 | 7.69 s | 8.11 s | 14.95 s | 2 | node-b |
| 1 | #6 | 9.71 s | 15.77 s | 23.02 s | 2 | node-b |
| 2 | #5 | 8.86 s | 15.71 s | 22.94 s | 2 | node-b |
| 2 | #6 | 9.67 s | 15.71 s | 22.94 s | 2 | node-b |

两遍的 `last_error` 都是 `lease expired`，`worker_id` 从 node-a 变为 node-b，`attempts` 从 1 变 2。

### 每节点完成数

| 遍 | node-a | node-b |
| :--- | ---: | ---: |
| 1 | 2 | 8 |
| 2 | 2 | 8 |

node-b 的 8 条里包含接管来的 #5、#6。node-a 少是因为它先启动、先把槽位占满，node-b 晚十几秒起来时前面的活已被领走——**拉模式按“谁闲谁领”，不按节点均分**，这是预期行为。

### 数据完整性

- 每条提交恰好一条 `judge_tasks` 记录，10 条 / 10 个不同 `submission_id`。
- 每条提交恰好 5 条 `test_results`，5 个不同 `ordinal`，没有多出来或重复的。
- 两遍的 6 项检查全部通过：无重复任务行、无超 2 次尝试、无卡死、两节点都完成过任务。

## 三、时间线（第 1 遍）

```
10:57:35.001  10 条提交全部成功，无 429
10:57:43.251  快照：node-a 2 条在跑 + 2 条已完成；node-b 2 条已完成；4 条排队
10:57:43.656  SIGKILL node-a
10:57:51.083  #5 回到待判（杀后 7.7 秒）
10:57:51.491  #5 被 node-b 认领
10:57:53.091  #6 回到待判（杀后 9.7 秒）
10:57:58.340  #5 判完
10:58:06.399  #6 判完，全部进入终态
```

从杀到第一条被重新捡起约 7.4 秒，正好落在“最后一次心跳之后的租约窗口”里：节点死了不会发任何通知（`SIGKILL` 连 FIN 都没有），系统只能从“它不再续租”推断出它已经不在了。

## 四、这套机制证明了什么

- **跨进程不会重复认领。** 8 条任务的尝试次数是 1，说明在两个独立进程之间，同一条任务只被成功认领过一次。条件更新 `WHERE id = ? AND status = 'QUEUED'` 的语义在跨进程时依然成立。
- **崩溃后任务会被接管，而且只接管一次。** 被强杀实例手上的 2 条任务尝试次数变为 2：一次是它自己认领，一次是新节点认领。没有出现 3 次，说明回收只触发一轮，没有反复抢。
- **接管不会写脏数据。** 用例结果没有翻倍、没有重复序号。

## 五、这套机制没有证明什么

写清楚边界，避免过度宣称：

- **网络分区**：两个实例连的是同一个 MySQL，没有把节点与数据库之间的网络切断。
- **时钟漂移**：两个进程在同一台机器上，共享同一个时钟。
- **数据库自身故障**：MySQL 是单点，它不可用时整套调度都停摆，租约机制救不了。
- **负载均衡**：本次只关心“不重复、能接管”，没有验证任务在两个节点间的均衡分布。

## 六、复现步骤

1. 建库并授权：`CREATE DATABASE judgex_node ...`，`GRANT ALL ON judgex_node.* TO 'judgex'@'%'`（Flyway 首次启动自动建表）。
2. 起两个实例，关键参数：

```bash
java -jar judgex-backend-1.0.0.jar \
  --server.port=18900 --judgex.worker.id=node-a \
  --judgex.worker.concurrency=2 \
  --judgex.worker.lease-seconds=10 --judgex.worker.heartbeat-interval-ms=1000 \
  --judgex.sandbox.mode=local \
  --spring.datasource.url=jdbc:mysql://127.0.0.1:3306/judgex_node...
```

第二个实例只改 `--server.port=18901 --judgex.worker.id=node-b`。

3. 登录（`student/student123`），向 `/api/submissions` 连发 10 条 Python 提交，源码 `sleep(1.2)` 后输出求和。
4. 等 8 秒，让两个节点都领到活；记下此刻每条任务的 `worker_id`。
5. `SIGKILL` 掉 node-a，每 0.5 秒查一次：

```sql
SELECT submission_id, status, attempts, worker_id FROM judge_tasks ORDER BY submission_id;
```

6. 预期：node-a 名下的任务在 10 秒租约到期后回到 `QUEUED`，被 node-b 认领，`attempts` 变为 2，最终 `DONE`。

## 七、复现时容易踩的坑

| 坑 | 现象 | 处理 |
| :--- | :--- | :--- |
| 同机两个 JVM 的 RocketMQ 客户端标识相同 | 两个实例互相把对方踢出消费组，看起来只有一个在消费 | 给每个实例传不同的 `-Drocketmq.client.name` |
| 新库没授权 | Flyway 报 `Access denied ... 1044` | 建库后补 `GRANT` |
| RocketMQ 在 JDK 17 下启动失败 | `InaccessibleObjectException` | 启动参数加 `--add-opens java.base/jdk.internal.ref=ALL-UNNAMED` 等 |
| 延时消息级别与租约不匹配 | 租约 10 秒、延时 30 秒，回收全靠扫描 | 实验里把延时级别调到 10 秒（生产两者一致） |
| PowerShell 5.1 读脚本中文乱码 | 脚本语法报错 | 脚本存成 UTF-8 **带 BOM** |
